# Languages

How the app is made ready for more than one language (ADR-220), and how to add
one. The code is the source of truth for the mechanics: `src/lib/i18n.ts`,
`src/lib/format.ts`, `lingui.config.ts`. This doc carries the rules and the
steps.

**Where it stands.** English is the one language shipped. The screens and the
`src/lib` copy are marked for translation (about 990 messages, 0.74.2); what
is left is listed under "What is still not converted". Adding a language is
now translating a catalog.

## The pieces

- **Lingui.** A message is written in English, in place, inside a macro. A
  Babel plugin (wired in `vite.config.ts`) turns it into a lookup by id at build
  time, and `lingui extract` collects every message into
  `src/locales/<locale>/messages.po`. Translators edit the `.po` file and
  nothing else.
- **One language per launch.** `main.tsx` calls `startI18n()` before the first
  render: it picks the best supported language from `navigator.languages`,
  fetches that catalog as a lazy chunk (the web bundle does not grow per
  language) and sets `<html lang>`. Changing the language is a reload, so there
  is no provider around the app and no re-render on change.
- **Formatting through `Intl`.** `src/lib/format.ts` writes numbers, averages,
  percents, ratios and dates in the active language. Never `toFixed`, a template
  ending in `%`, or `toLocaleDateString`: a test of `en` cannot see that `187.5`
  is `187,5` in German.

## Marking a string

Use the macros from `@lingui/core/macro`, and read them in render or in a
function, never in a module-level constant (a constant is built at import,
before the language is chosen).

```tsx
import { plural, t } from "@lingui/core/macro";

<h1>{t`Settings`}</h1>
<button aria-label={t`Edit game lanes`}>

// A variable in a message is named by its variable. A property access is not
// a name, so give it one:
t`Game ${{ gameNumber: game.game_number }} is in the books.`

// Counts are plurals, one whole message per form, with # for the number:
plural(days, { one: "# day ago", other: "# days ago" })
```

A sentence with markup in it (a bold word, an icon) is one `<Trans>` from
`@lingui/react/macro`, never `t` pieces around the element:

```tsx
import { Trans } from "@lingui/react/macro";

<Trans>
  You leave <span className="font-semibold">{askedLeave}</span> most often.
</Trans>
// msgid "You leave <0>{askedLeave}</0> most often."
```

The translator sees the elements as numbered tags and can move them. A variable
inside is named by its identifier, so read a property into a local first.
There is no provider: `lingui.config.ts` points the compiled macro at
`src/lib/i18nTrans.tsx` (through the `@headpin/trans` alias in
`vite.config.ts`), which reads the global `i18n` like `t` does (ADR-223).

Rules that keep a catalog translatable:

1. **One whole sentence per message.** Never build a sentence from pieces
   (`"Last backup " + age`): the order of the parts is the language's. Where a
   phrase had a variable fragment, write a message per case
   (`describeLastBackup` in `src/lib/backupNudge.ts`).
2. **Plurals through `plural()`**, never `n === 1 ? "game" : "games"`. Other
   languages have more forms than two.
3. **A list built at import uses `msg`**, which makes a descriptor, and the
   screen reads it with `i18n._(descriptor)` in render (`NAV_ITEMS` in
   `App.tsx`, `TEXT_SIZES`).
4. **Numbers and dates go through `format.ts`.**
5. **Do not translate** the app's name, a ball's name or brand, a pattern's
   name, or the stored text a bowler typed.
6. **Bowling terms get a comment** so the translator knows it is a term, not a
   word: `t({ message: "Strike", comment: "A bowling term: ..." })`. Strike,
   spare, foul, pocket, split and the leave names are messages like any other;
   a language that bowls will have its own words, and one that does not will
   want to keep the English and say so in the comment. The comment appears in
   the `.po` file above the entry.
7. **Where the same word means two things**, give each its own `context`:
   `t({ message: "Back", context: "navigation" })`.

## Extract, check

```
npm run i18n:extract    writes src/locales/*/messages.po from the source
npm run i18n:check      fails if the catalogs are out of date (it is in verify and CI)
```

A string marked, changed or deleted changes the catalog, so the extract is
committed with the change. The check fails with the catalogs already
re-extracted: review and commit them.

## Adding a language

For a language with code `ja`:

1. `lingui.config.ts`: add `"ja"` to `locales`.
2. `src/lib/i18n.ts`: add `"ja"` to `SUPPORTED_LOCALES`.
3. `npm run i18n:extract`, which creates `src/locales/ja/messages.po` with every
   message untranslated.
4. Translate the `msgstr` of each entry. Keep the placeholders (`{name}`,
   `#`) and give a plural all of the forms the language has (the `.po` header
   `Plural-Forms` says which).
5. **iOS.** Add `<string>ja</string>` to `CFBundleLocalizations` in
   `ios/App/App/Info.plist`. Until a language is listed there the phone does
   not offer it for the app in Settings, Headpin, Language, and
   `navigator.languages` will not carry it. Add the same to the App Store
   listing's localizations when it is to be sold in that language
   (`docs/APP-STORE-LISTING.md`).
6. **Android.** The web view takes `navigator.languages` from the phone; nothing
   to declare. Declaring `resConfigs`/`localeConfig` is only needed for the
   system's per-app language picker, and has not been set up.
7. A language written right to left (Arabic, Hebrew) also needs layout work the
   app has not had: the back chevron, the sliding screens and the board
   numbers all assume left to right. Plan it as design work, not a catalog.
8. Check the screens at 360px: German and Finnish run longer than English.
   Layouts that fit by luck (the tab bar, the scorecard, the stats columns)
   will show it first.

The `.po` format is read by every translation tool. The catalog for a language
is a lazy chunk, so adding one costs a bowler who does not use it nothing.

## What is still not converted

`node scripts/i18n-unconverted.mjs` prints the count by file. After 0.74.2 it
reports about 24 hits in 17 files, and those are false positives: example
placeholders ("Pinecrest Lanes"), an `alt` that is a ball name, comment text,
the app's name. The count is a heuristic and misses anything built in a helper.

Not counted at all, and each a project of its own:

- **Static content**: `src/lib/guides.ts` (the guide articles), the legal pages
  (`src/lib/legalPage.ts`), the landing page (`index.html`) and the pages
  generated from them. These are long prose and want a catalog (or a file) per
  language, not a message per sentence.
- **Data**: the ball catalog and oil pattern names, which are proper names.
- **Chart and diagram labels** drawn in SVG, and the descriptions the diagrams
  read to a screen reader (`BallLayoutDiagram`).
- **The native tab bar** takes its titles from the page (`nativeTabItemsOnce`
  in `App.tsx`), so it follows the language; the Home Screen quick actions in
  `Info.plist` and the App Store listing do not and need their own
  localizations.
- The copy rules in `src/test/copy.test.ts` check English wording and will need
  to read the source language only.
